# 로드맵

> 원본은 `.github/handbook/ROADMAP.md` 하나뿐이다. 각 레포는 이 파일을 참조만 한다.
> 레포 태그: `[api]` shop-sim-api · `[web]` shop-sim-web · `[infra]` shop-sim-infra · `[vendor]` shop-sim-vendor · `[loadtest]` shop-sim-loadtest · `[both]` api + web
> 화면 표기: **스토어**(구매자) · **셀러센터**(판매자) · **어드민**(플랫폼 운영자)
> 항목은 착수할 때 GitHub Issue로 옮기고, 이슈 번호를 항목 끝에 적는다. (예: `… (#12)`)
> 시스템 구성·계약·도메인 모델·배포 환경은 `architecture.md`, 결정 근거는 `adr/`에 있다.

각 단계는 **API · 화면 · 배포까지 관통하는 수직 슬라이스**로 끝낸다. 단계가 끝나면 실서버에 배포된 상태여야 한다.

- [x] `[api]` `openapi/` 스펙 작성: 헬스체크, 상품 단건/목록 조회 (2026-10-29, shop-sim-api#26 — 경로 접두어 없음(API는 하위 도메인), 스펙 린트는 `pnpm lint`에 포함)
- [x] `[api]` 스펙 린트 + 서버 인터페이스 생성 파이프라인 (2026-10-29, shop-sim-api#28 — `redocly bundle` → Hey API, 생성물은 커밋하지 않음)

## 2단계 — 회원 · 인증 · 판매자 입점

- [ ] `[api]` 계정 모델: 모든 일반 계정은 구매자. **판매자는 같은 계정에 판매자 프로필(Seller)을 추가**하는 방식(1계정 1스토어). 플랫폼 운영자(ADMIN) 계정은 일반 계정과 분리
  - 권한 판단은 "역할 문자열"이 아니라 "이 요청이 어떤 컨텍스트(구매/판매)인가 + 리소스 소유자인가"로 한다
  - 정책: 자기 스토어 상품은 구매·리뷰·쿠폰 사용 불가 (리뷰 조작·자전거래 방지)
- [ ] `[api]` 인증: Better Auth 연결(ADR 0015 — DB 세션으로 결정, JWT 안 씀), 이메일 가입·로그인·로그아웃, 운영자 인스턴스(가입 차단, 시드로 첫 운영자)
- [ ] `[api]` **소셜 로그인**: Google, Kakao, Naver (OAuth 2.0 Authorization Code + PKCE, 계정 연결)
- [ ] `[api]` 판매자 입점: 신청(상호, 사업자 정보, 정산 계좌는 마스킹 저장) → 어드민 승인/반려 → 스토어 생성
- [ ] `[api]` 판매자 스토어 정보: 스토어명, 소개, 브랜드 이미지, 배송 정책(기본 배송비, 무료배송 기준, 출고지)
- [ ] `[api]` 권한 검사: 판매자는 자기 상품·주문만 접근 (리소스 소유권 검사를 한 곳에서)
- [ ] `[web]` 스토어: 로그인(소셜 3종), 회원가입, 마이페이지 뼈대, **"판매자 입점하기" / "셀러센터로 이동"** 진입점
- [ ] `[web]` 셀러센터: 같은 계정으로 로그인(SSO), 입점 신청, 판매자 정보 관리, "스토어로 이동" 전환
- [ ] `[web]` 어드민: 입점 심사 그리드(승인/반려), 회원·판매자 목록

## 3단계 — 카탈로그 · 상품 에디터 · 검색

- [ ] `[api]` 상품 CRUD (판매자 소유), 카테고리, 옵션/SKU 모델
- [ ] `[api]` 상품 필드: 상품명, 부제, 카테고리, **상품 타입(완제품/제작상품)**, 가격, **할인율**, 상세 본문, 상품 정보 고시, 재고 수량, **제작 리드타임**(제작상품)
- [ ] `[api]` **제작 옵션**: 자유 입력형 옵션(예: 각인 문구, 이름) 정의 → 주문 시 입력값 스냅샷
- [ ] `[api]` 이미지 업로드: 여러 장 한 번에, presigned URL → 업로드 완료 콜백 → 워커에서 리사이즈·썸네일. **첫 번째 이미지가 대표 이미지**
- [ ] `[api]` ABO 시드 스크립트: 가상 판매자 여러 명에게 상품을 나눠 **실제 업로드 API 흐름을 그대로 타게** 임포트
- [ ] `[api]` 편집 워크플로: 임시저장, 발행/예약 발행, 버전 이력(ProductRevision)
- [ ] `[api]` 동시 편집 충돌 방지 (낙관적 락, version 컬럼 → 409 응답)
- [ ] `[api]` **아웃박스 + Kafka 기반 구축** (상품 변경이 첫 번째 이벤트): 같은 트랜잭션에서 `outbox` 기록 → 폴링 릴레이 → `product.events` (키: `productId`). 5단계 주문 이벤트도 이 기반을 그대로 쓴다
- [ ] `[api]` **이벤트 계약**: `product.events`를 AsyncAPI 스펙으로 먼저 정의(스키마, `ce_type` 메이저 버전, 키 — `asyncapi/CONVENTIONS.md`) → 리뷰 → 구현. 호환성 스크립트(`poc/event-contract`)를 main으로 옮겨 CI 필수 검사로 건다(main과 양방향 비교)
- [ ] `[api]` **검색 인덱스 설계 (OpenSearch)**

## 4단계 — 재고 관리 (원재료 · 로트 · 유효기한)

참고 프로젝트의 "원재료·완제품 통합 관리, 유통기한 임박 알림"을 일반화해서 넣는다.

- [ ] `[api]` 재고 단위: **완제품 재고** + **원재료 재고**
- [ ] `[api]` **BOM(레시피)**: 제작상품 1개당 필요한 원재료와 수량 → 제작상품 판매 시 원재료 차감
- [ ] `[api]` **로트(입고 단위)**: 입고일, 수량, **유효기한** → 차감은 유효기한 빠른 순(FEFO)
- [ ] `[api]` 재고 조정 이력: 입고, 판매 차감, 폐기, 실사 조정 — 모든 변동을 원장(ledger)으로 기록하고 현재고는 원장 합계와 일치
- [ ] `[api]` **유효기한 임박 감지**: 매일 배치로 D-7 / D-3 / 만료 로트 탐지 → 판매자 알림(8단계 연결), 만료 로트 자동 판매 제외
- [ ] `[api]` 재고 부족 임계치 → 판매자 알림
- [ ] `[web]` 셀러센터 **재고 관리 탭**: 완제품·원재료 그리드, 로트별 유효기한(임박 강조), 입고 등록, 조정 이력, BOM 편집

## 5단계 — 주문 · 결제 (+ 이벤트 기반 처리의 뼈대)

- [ ] `[api]` 장바구니: 판매자별로 묶어 표시 (비회원/회원)
- [ ] `[api]` **주문 분할**: 결제 1건(주문서) → 판매자별 주문(배송 단위) → 주문 항목
- [ ] `[api]` **배송비**: 판매자별 기본 배송비, 무료배송 기준 금액, (선택) 도서산간 추가 배송비
- [ ] `[api]` **쿠폰**: 플랫폼 쿠폰(어드민 발행) + 판매자 쿠폰(판매자 발행), 정액/정률, 최소 주문 금액, 발급·사용 이력, 중복 사용 방지
- [ ] `[api]` 주문 생성: 가격·할인·제작 옵션 입력값 스냅샷
- [ ] `[api]` **재고 예약 모델**: 주문 생성 시 예약(reserve) → 결제 완료 시 확정(confirm) → 실패·타임아웃 시 해제(release). 가용 재고 = 재고 − 미확정 예약 합계. 제작상품은 원재료 기준으로 예약
- [ ] `[api]` 재고 동시성: 초과 판매 없음 (조건부 UPDATE / 행 락 / 낙관적 락+재시도 비교) + 동시성 테스트
- [ ] `[api]` **결제 포트**: `PaymentGateway` 인터페이스(승인, 취소·부분취소, 조회, 웹훅 검증). 도메인은 포트만 안다
- [ ] `[api]` **토스페이먼츠 어댑터** (테스트 키): 결제 위젯 결제 → 리다이렉트로 받은 값 검증(금액 위변조 확인) → 승인 API 호출
- [ ] `[api]` **모의 PG 어댑터**: shop-sim-vendor의 모의 PG 호출
- [ ] `[api]` PG 라우팅: 시뮬레이터 봇 계정은 모의 PG, 사람은 토스페이먼츠 (설정으로 강제 전환 가능)
- [ ] `[vendor]` **모의 PG**: 토스페이먼츠와 **같은 형태**의 승인·취소·조회 API와 오류 코드, 웹훅 발송, 자체 OpenAPI 스펙 공개
- [ ] `[api]` 결제 웹훅 멱등성 (idempotency key)
- [ ] `[api]` 주문·결제 이벤트를 3단계 아웃박스 기반 위에 추가 (`order.events`, `payment.events`, 키: `orderId`) — AsyncAPI 스펙 먼저
- [ ] `[api]` 주문·결제 이벤트 흐름: `OrderCreated` → (재고 예약 · 결제 정보 생성) → 결제 승인 → `PaymentCompleted` → 판매자별 주문·배송 정보 생성, 재고 확정, 상태 `PAID`

## 6단계 — 배송 · 물류 서버

`shop-sim-vendor`의 `logistics-sim`이 택배사 역할을 한다. 우리 회사 입장에서는 **남의 시스템**이라, 공개된 API 문서만 보고 연동한다.

- [ ] `[vendor]` `logistics-sim` (택배사 역할, 자체 DB, 자체 OpenAPI 스펙 공개)
  - 운송장 생성 API: 택배사(우체국, CJ대한통운, 한진, 로젠, 롯데) + 운송장 번호 → 추적 생성
  - 상태 진행: `PICKED_UP → AT_SORT_HUB → DEPARTED_HUB → OUT_FOR_DELIVERY → DELIVERED`
  - 예외 상태: `DELAYED`, `DELIVERY_FAILED`(부재), `RETURNED`
  - 스케줄러가 상태를 진행시키고, 단계별 소요 시간은 **시간 압축 배율**로 조절 (실제 하루 → 수 분)
  - **배송 상태 수동 변경 API** (시연·테스트용)
  - 현황 조회 API: 접수 / 배송중 / 배송완료 건수, 운송장 목록
  - 추적 이력(TrackingLog) 조회 API
  - 장애 주입 API: 웹훅 실패율, 지연, 상태 누락, 중복 발송
- [ ] `[vendor]` 물류 서버 자체 콘솔(간단한 웹 화면): 운송장 생성·조회, 접수/배송중/완료 현황, 상태 수동 변경, 장애 주입 토글
- [ ] `[api]` 메인 API ← 물류 서버 연동 (두 가지 패턴 모두 구현해 비교)
  - **웹훅(푸시)**: 상태 변경 시 메인 API로 전송, HMAC 서명 검증, 재시도(지수 백오프), 멱등 처리, 순서 뒤바뀜 처리(이전 상태로 되돌리지 않기)
  - **대사(폴링)**: 주기 작업이 배송 중 주문을 조회해 웹훅 누락을 보정 (참고 프로젝트는 이 방식만 사용)
  - **수동 동기화 API**: 판매자가 자기 배송중 주문을 즉시 대사
- [ ] `[api]` 판매자 출고 흐름: 주문 확인 → 상품 준비 → (출고 지연 처리) → 운송장 등록 → `READY_FOR_SHIPMENT` → 물류 접수 시 `IN_DELIVERY` → `DELIVERED`
- [ ] `[api]` 배송 상태 변경 → 아웃박스 이벤트 (8단계 알림의 입력)
- [ ] `[web]` 스토어: 배송 조회 타임라인
- [ ] `[web]` 셀러센터 **주문/배송 관리**: 상태별 주문 현황 카드, 기간·배송 상태 검색 그리드, 상태 일괄 변경, 출고 지연 처리(사유·예정일), 택배사·운송장 일괄 등록, **"배송중 주문 업데이트" 버튼**
- [ ] `[web]` 어드민: 배송 현황 대시보드(상태별 건수, 지연 건, 택배사별 평균 소요 시간)

## 7단계 — 시뮬레이터 (기본)

이후 단계(알림, 채팅, 리뷰, 정산, 수요 예측)는 시뮬레이터가 만든 데이터를 재료로 쓴다. 각 단계에서 시나리오를 추가한다.

- [ ] `[loadtest]` 가상 판매자 봇: 신규 주문 확인 → 준비 → 운송장 등록 (판매자별 처리 속도·출고 지연률 파라미터)
- [ ] `[loadtest]` 시나리오 엔진: 동시 접속 수, 세일 이벤트(특정 상품 폭증 → 재고 경합), 재고 부족, 쿠폰 남용, 결제 단계 이탈(타임아웃), 취소·반품 요청률
- [ ] `[loadtest]` **과거 데이터 생성 모드**: 지난 90일치 주문 이력을 요일·계절성·추세 패턴으로 생성해 JSONL 파일로 출력 (12단계 수요 예측의 학습 데이터)
- [ ] `[api]` **주문 이력 백필 스크립트**: loadtest가 만든 JSONL을 도메인 서비스로 적재(과거 시각 지정, 봇 계정 한정, 재실행해도 중복 없게)
- [ ] `[vendor]` 모의 PG 장애율·지연 주입 API
- [ ] `[vendor]` 물류 서버 시나리오: 배송 지연 폭증, 웹훅 장애, 택배사별 지연
- [ ] `[loadtest]` 시뮬레이션 실행 상태 저장 (자체 저장소 — 제품 DB에 쓰지 않는다)
- [ ] `[loadtest]` 시뮬레이터 **컨트롤 패널**(자체 웹 UI): 시나리오 켜기/끄기, 파라미터 실시간 조절, 벤더 장애 주입 토글
- [ ] `[api]` 봇 계정 식별(테스트 계정 플래그) — 통계·정산에서 구분 가능하게

- [ ] `[api]` **멀티 인스턴스 팬아웃**: Redis Pub/Sub(`notify:{userId}` 채널)로 다른 인스턴스에 붙은 연결에도 전달. 참고 프로젝트의 Redis Stream 방식과 9단계에서 비교 (아래 심화)
- [ ] `[api]` 알림 목록(커서 페이지네이션), 읽음 처리(단건·전체), 안 읽은 수
- [ ] `[api]` (선택) 이메일 채널: 로컬은 Mailpit
- [ ] `[web]` 스토어·셀러센터·어드민 **상단 알림**: 벨 아이콘 + 안 읽은 수, 토스트, 목록, 읽음 처리
- [ ] `[web]` SSE 연결 관리: 재연결, 탭 여러 개일 때 중복 연결 처리, 백그라운드 탭 처리

## 9단계 — 채팅 · 고객센터

- [ ] `[api]` 실시간 게이트웨이: Nest WebSocket 게이트웨이 (Socket.IO 또는 ws — 착수 시 결정), 핸드셰이크 인증
- [ ] `[api]` 멀티 인스턴스: Redis 어댑터 또는 Redis Pub/Sub로 메시지 팬아웃
- [ ] `[api]` **구매자 ↔ 판매자 1:1 채팅** (Postgres): 방별 마지막 메시지·안 읽은 수 비정규화, 읽음 시각, 퇴장 처리
  - 참고 프로젝트는 MongoDB + Redisson 분산 락을 썼다. 여기서는 Postgres 유니크 제약(구매자·판매자 쌍)으로 방 중복 생성을 막고, 필요한 경우에만 분산 락을 비교 실험
- [ ] `[api]` **주문 정보 연동**: 주문 상세에서 시작하면 해당 주문 카드가 첫 메시지로 첨부, 판매자 화면에 구매자의 해당 판매자 주문 내역 표시
- [ ] `[api]` 메시지 이력: `(room_id, created_at)` 인덱스 + 커서 페이지네이션(위로 스크롤)
- [ ] `[api]` 읽음 확인(read receipt), 접속 상태(presence), 입력 중 표시
- [ ] `[api]` 새 메시지 → 오프라인 수신자에게는 8단계 알림으로 전달
- [ ] `[api]` **고객센터 (플랫폼 ↔ 사용자)**: 공지사항(첨부), FAQ(카테고리), 1:1 문의(첨부, 답변, 긴급도 자동 상향), 신고 접수·처리
- [ ] `[web]` 스토어: 판매자에게 문의하기(상품·주문 상세에서 시작), 채팅 목록·대화창
- [ ] `[web]` 셀러센터 **고객관리**: 채팅 목록, 대화창 + 구매자 주문 내역 사이드 패널, 응답 시간 표시
- [ ] `[web]` 스토어·셀러센터 상단 메뉴: **공지사항, FAQ, 1:1 문의**
- [ ] `[web]` 어드민: 공지·FAQ 작성, 문의 답변 콘솔(긴급도 정렬), 신고 처리
- [ ] `[web]` 연결 끊김·재연결 시 메시지 누락 복구, 낙관적 전송 표시(전송 중/실패/재전송)
- [ ] `[loadtest]` 구매자 봇 문의 발생률, 판매자 봇 응답 시간 분포

## 10단계 — 리뷰 · LLM 리뷰 요약

- [ ] `[api]` 리뷰: 배송 완료 주문 항목에만 작성, 별점, 이미지, 수정·삭제, 판매자 평점 집계
- [ ] `[api]` **LLM 리뷰 요약 배치** (매일 0시)
  - 상품마다 **최신 리뷰 30개** 조회
  - **변경 감지**: 마지막 요약 이후 새 리뷰·수정·삭제가 없으면 건너뜀 (마지막 반영 리뷰 ID/해시 저장)
  - **1단계**: 광고·무의미한 리뷰 필터링 + 긍정/부정 분류 (구조화 출력: JSON 스키마로 강제)
  - **2단계**: 긍정·부정 각각 한 줄 요약
  - 실패 처리: 재시도, 상품 단위 격리(한 상품 실패가 배치 전체를 멈추지 않게), 호출 수·토큰 비용 기록
  - 배치 실행 이력과 처리·건너뜀·실패 건수 기록
- [ ] `[api]` **제공자 독립 LLM 계층** (어떤 모델이든 설정으로 교체)
  - 도메인 코드는 `LlmClient` 포트(인터페이스)만 안다: `generateStructured(schema, prompt)`, `generateText(prompt)`
  - 어댑터 1: AI SDK(Vercel) 기반 — OpenAI, Anthropic, Google 등 공식 제공자 패키지를 그대로 사용
  - 어댑터 2: **OpenAI 호환 HTTP** — Ollama·vLLM·LM Studio 같은 로컬 모델, OpenRouter 등 게이트웨이까지 base URL만 바꿔 연결
  - 어댑터 3: 가짜 구현 — 테스트·로컬에서 비용 없이 결정적 응답
  - 단계별 모델 지정: 1단계(필터·분류)는 저렴한 모델, 2단계(요약)는 더 좋은 모델 — 설정 파일로
  - 구조화 출력 보장: 제공자가 JSON 스키마 출력을 지원하면 사용, 아니면 JSON 모드 + 스키마 검증 + 재시도로 폴백
  - 호출마다 제공자·모델·프롬프트 버전·토큰·지연 시간·실패 사유 기록 → 모델 교체 전후 품질·비용 비교
  - 타임아웃, 재시도(지수 백오프), 제공자별 동시 호출 수 제한
- [ ] `[api]` 모델 비교 실험: 같은 리뷰 세트로 2~3개 모델(상용 1 + 로컬 1 이상) 요약 결과·비용·지연 비교
- [ ] `[web]` 스토어 상품 상세: 리뷰 목록, **AI 리뷰 요약(긍정 한 줄·부정 한 줄)**
- [ ] `[web]` 셀러센터: 내 상품 리뷰, 리뷰 요약 모아 보기
- [ ] `[web]` 어드민: 배치 실행 이력, 수동 실행 버튼
- [ ] `[loadtest]` 배송 완료 후 리뷰 작성 봇 — 긍정·부정·**광고·무의미 리뷰를 섞어** 생성해 1단계 필터를 검증

## 11단계 — 정산 · 판매 분석

- [ ] `[api]` 수수료 정책: 판매 수수료율(기본·카테고리별), 결제 수수료
- [ ] `[api]` **월별 정산 배치**: 구매 확정(배송 완료 + N일, 반품 제외) 건 집계 → 판매자별 정산 금액 = 판매액 − 수수료 − 쿠폰 판매자 부담분 + 배송비. 청크 단위 처리, 재실행해도 결과가 같게(멱등)
- [ ] `[api]` 정산 상태: 정산 예정 → 정산 완료, 정산 내역·명세
- [ ] `[api]` **정산 내역·통계 CSV 다운로드**: 스트리밍 생성(대용량에서도 메모리 일정), 한글 엑셀 호환(UTF-8 BOM)
- [ ] `[api]` 판매 분석: 기간별 매출, 상품별 매출, **월간 상품 매출 TOP10**, 오늘 주문 수·매출
- [ ] `[web]` 셀러센터 **대시보드**: 오늘 주문 수·매출, **주간 매출 추이**, **월간 상품 매출 TOP10**, 수요 예측 결과·발주 추천(12단계)
- [ ] `[web]` 셀러센터 **정산관리**: 월별 정산 내역, 명세, CSV 다운로드
- [ ] `[web]` 어드민: 판매자별 정산 현황 그리드, 정산 배치 실행 이력, 플랫폼 거래액 대시보드

## 12단계 — 수요 예측 · 발주 추천

- [ ] `[api]` **일별 판매 집계 배치**: 상품별 일 판매량 테이블 (판매 0인 날도 0으로 채움)
- [ ] `[api]` **수요 예측 배치** (매일 0시): 상품별 **오늘부터 7일간 판매량** 예측
  - 기초 알고리즘: **이동평균**, **지수평활법**(단순 → 추세 반영 홀트 방식까지), 요일 계절성
  - 모델별 과거 구간 백테스트로 오차(MAE, MAPE) 기록 → 상품별로 오차가 작은 모델 선택
- [ ] `[api]` **발주 추천**: 재주문점 = 리드타임 동안 예측 수요 + 안전재고. 현재고(가용) ≤ 재주문점이면 발주 추천 + 추천 수량. 제작상품은 BOM으로 원재료 발주량까지 환산
- [ ] `[api]` 발주 추천 → 판매자 알림 (8단계 연결)
- [ ] `[web]` 셀러센터 대시보드: **예측 판매량과 현재 재고를 나란히** 보여주는 차트, 발주 추천 상품 목록
- [ ] `[web]` 셀러센터 재고 관리: 상품별 예측 곡선 + 실제 판매 비교, 예측 오차 표시
- [ ] `[web]` 어드민: 예측 배치 실행 이력, 모델별 오차 분포

## 13단계 — 관측성 · 대시보드

- [ ] `[api]` 구조화 로그, OpenTelemetry 계측 (분산 트레이스: web → api → worker → 벤더 API)
- [ ] `[infra]` Prometheus(지표), Loki(로그), OTel Collector 구성, Sentry 프로젝트 연결
- [ ] `[infra]` 장애 대응 런북, 포스트모템 템플릿 → 시뮬레이터로 장애를 일으켜 대응 연습
- [ ] `[api]` 지표: 아웃박스 적체·릴레이 지연, 검색 색인 지연, **Kafka 컨슈머 랙(그룹·파티션별)**, DLT 적재 수, SSE·WebSocket 동시 연결 수, 웹훅 실패·재시도 수, 배치 소요 시간·실패 수, LLM 호출 수·비용
- [ ] `[web]` 스토어·셀러센터·어드민 Sentry, 웹 바이탈 수집
- [ ] `[web]` 어드민 **플랫폼 운영 대시보드**: 거래액·주문 실시간 추이(시계열, 다운샘플링, 범위 줌), 판매자별 순위, 재고·유효기한 위험 상품, 예측 vs 실제
- [ ] `[web]` 어드민 **시스템 모니터링 대시보드**: API 지연, 에러율, 아웃박스 적체, Kafka 컨슈머 랙, 결제 실패율, 실시간 연결 수 — Prometheus/Loki API를 직접 붙인 자체 UI
- [ ] `[web]` 로그 뷰어: 가상 스크롤, 필터, 실시간 tail
- [ ] `[web]` 알림 규칙 설정 UI (8단계 어드민 알림과 연결)
- [ ] `[web]` 실시간 주문 그리드: `applyTransactionAsync` 배치 업데이트, 셀 플래시, 갱신 중 정렬·필터 유지

## 14단계 — 심화

- [ ] `[loadtest]` k6 부하 테스트 → 대시보드에서 병목 관찰·개선 (채팅·SSE 동시 연결 부하 포함)

- [ ] `[api]` (선택) 이벤트 스키마 레지스트리 도입: JSON Schema/Avro로 이벤트 호환성 검사
- [ ] `[api]` Kafka 심화: 파티션 늘리기·리밸런싱 관찰, 컨슈머 장애 시 랙 회복, 이벤트 재처리(오프셋 리셋)로 통계 재계산
- [ ] `[api]` 알림 팬아웃: Redis Pub/Sub vs **Redis Stream**(참고 프로젝트 방식) 비교 — 메시지 보존, 소비자 그룹, 재연결 시 재전송
- [ ] `[api]` 검색 심화: 랭킹 튜닝(정확도 + 판매량·평점·최신성 가중치, function score), 검색 품질 지표(클릭률, 무결과 검색어), 오타 교정, 색인 경로를 CDC로 교체

- [ ] `[web]` ABO 360도 이미지 뷰어

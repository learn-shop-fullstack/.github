# ADR 0001: 레포 구조: 제품 2 + 플랫폼 1 + 외부 1 + 테스트 도구 1 + 조직 메타

- 상태: 채택
- 날짜: 2026-10-28

## 맥락

회사에서 일한다고 가정하고 학습한다. 처음에는 백엔드·프론트 2개 레포였지만, 실제 회사라면 인프라 코드, 외부 회사 시스템, 테스트 도구를 제품 코드와 같은 레포에 두지 않는다.

## 결정

레포를 6개로 나눈다: `.github`(핸드북·템플릿), `shop-sim-api`, `shop-sim-web`, `shop-sim-infra`, `shop-sim-vendor`, `shop-sim-loadtest`. 레포 간 연결은 버전이 붙은 스펙으로만 한다.

## 결과

- 인프라와 앱 코드의 권한·배포 주기를 분리하는 회사 표준을 경험한다. GitOps 전환이 자연스럽다
- 외부 시스템(PG, 택배사)을 공개 API 문서만 보고 연동하는 현실적인 경계가 생긴다
- 대가: 한 기능이 여러 레포의 PR로 나뉜다. 스펙 버전 관리·업그레이드 PR이 필요하다

## 검토한 대안

- 2개 레포 유지: 단순하지만 인프라·외부 시스템·테스트 도구가 제품 레포에 섞인다
- 모노레포 1개: 혼자 하기엔 가장 편하지만 레포 간 계약 관리 경험이 사라진다
- 팀별 레포(6개 이상): 가상의 여러 팀을 시뮬레이션하는 것은 목표가 아니다

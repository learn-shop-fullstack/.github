# ADR 0012: 스펙 우선 툴체인 확정: Hey API nestjs 타입 + express-openapi-validator + Problem Details 필터

- 상태: 채택
- 날짜: 2026-10-28

## 맥락

ADR 0003은 스펙 우선 방식과 도구 후보를 정했지만, Hey API `nestjs` 플러그인이 베타라 0단계 POC(shop-sim-api#2)로 검증하기로 했다. 그사이 NestJS 12가 나왔고 플러그인 문서는 v11만 명시한다. 런타임 검증은 대안 두 개(`@nest-openapi/validator`, Hey API Zod 플러그인 + 파이프·인터셉터)와 같은 사례로 비교했다.

## 결정

- **컴파일 타임**: Hey API `@hey-api/openapi-ts`(`@hey-api/typescript` + `nestjs` 플러그인)로 타입을 생성하고 컨트롤러가 `implements Pick<XxxControllerMethods, ...>`로 구현한다. 0.x라 정확한 버전으로 고정한다.
- **런타임**: `express-openapi-validator`를 Nest 미들웨어로 전 경로에 걸고, 요청·응답·`format`을 검증한다. 응답 검증은 모든 환경에서 켠다.
- **에러 응답**: 전역 `@Catch()` 필터가 모든 예외를 RFC 9457 `application/problem+json`으로 바꾼다. 4xx는 `detail`에 원인을 담고, 5xx는 메시지를 숨기고 로그로만 남긴다.
- **생성물**: 커밋하지 않는다. `prebuild`로 빌드마다 생성한다. 계약 변화는 YAML diff로 리뷰한다.
- **버전**: NestJS 12(POC는 12.2.0), TypeScript 6(Nest 12 CLI 기준), OpenAPI 3.1.

## 결과

- 스펙 변경(이름·타입·필수 필드·파라미터)은 빌드에서, 형식·범위 위반은 런타임에서 잡힌다. OpenAPI 3.1 문법 7종을 두 도구 모두 정확히 처리한다
- 스펙에 엔드포인트를 추가하면 코드 없이도 검증되고, 에러 응답까지 계약으로 검증된다
- 대가와 보완책
  - 검증기 오류는 `HttpException`이 아니라 필터 없이는 모두 500이 된다 → 필터 필수
  - `additionalProperties: false`가 없으면 응답의 초과 필드(내부 필드)를 잡지 못한다 → 스펙 규약으로 강제(shop-sim-api#6)
  - `required`에만 있고 `properties`에 없는 필드는 생성기가 조용히 무시한다 → 스펙 린트로 잡는다(#6)
  - `Pick`에 넣지 않은 새 엔드포인트는 빌드가 실패하지 않는다(런타임 검증은 동작)
  - 런타임에 YAML이 필요하다 → 배포 이미지에 `openapi/`를 포함
  - 응답 검증 비용은 측정하지 않았다 → 7단계 시뮬레이터, 14단계 k6에서 측정 후 재검토
  - Nest 12는 플러그인 문서의 지원 범위 밖이다. 생성물이 순수 타입이라 동작했지만 업그레이드 시 다시 확인한다

## 검토한 대안

- `@nest-openapi/validator` 0.1.2: 요청·응답·3.1 검증은 같지만, 던진 예외(에러 응답)를 검증하지 않고, Nest 12가 peer 범위(^9~^11) 밖이며, 사용자가 적다
- Hey API Zod 플러그인 + 파이프·인터셉터: 런타임에 YAML이 필요 없고 초과 필드를 지워 유출을 막지만, 엔드포인트마다 직접 붙여야 하고 빠뜨려도 빌드가 통과한다. 생성 과정에서 `format: uri-reference`가 경고 없이 빠지고 에러 응답 스키마가 생성되지 않는다. 클라이언트 쪽 검증 용도로는 web 클라이언트 도구 결정(shop-sim-web#1)에서 다시 본다

# ADR 0016: 이벤트 계약: CloudEvents binary 봉투, 양방향 호환성 검사, Schema Registry 없음

- 상태: 채택
- 날짜: 2026-10-28

## 맥락

ADR 0003은 Kafka 이벤트도 AsyncAPI로 스펙 우선 관리한다고 정했지만, 메시지의 봉투(메타데이터를 어디에 어떻게 싣는가)와 CI에서 하위 호환을 판정할 도구는 정하지 않았다. 이벤트는 컨슈머 그룹이 늘수록, 그리고 오프셋 리셋으로 옛 메시지를 다시 읽을 수 있어서(ADR 0004) 계약을 깨는 비용이 HTTP보다 크다. POC(shop-sim-api#7)로 봉투 형식과 판정 도구 세 가지를 실제 사례로 비교했다.

## 결정

세부 규칙의 원본은 `shop-sim-api/asyncapi/CONVENTIONS.md`다. 여기에는 되돌리기 어려운 선택만 적는다.

- **봉투**: CloudEvents 1.0 Kafka 프로토콜 바인딩의 binary 모드. 속성은 `ce_` 헤더, 이벤트 데이터는 메시지 값(순수 JSON). AsyncAPI 메시지 트레이트 하나로 모든 메시지에 적용한다.
  - `ce_id`는 아웃박스 행 ID로 컨슈머의 멱등 키다
  - `ce_type`은 `<집계>.<사건>.v<메이저>`로 메시지와 1:1이고 바꾸지 않는다
  - 키는 집계 ID다
- **호환성 원칙**: 생산자는 닫힌 스키마(`additionalProperties: false`)로 검증해 보내고, 컨슈머는 모르는 필드와 모르는 enum 값을 무시한다. 판정은 두 방향을 모두 본다. 하나는 옛 컨슈머가 새 메시지를 받는 방향, 다른 하나는 새 컨슈머가 옛 메시지를 재처리하는 방향이다. 그래서 선택 필드 추가·enum 값 추가만 호환이고, 필수 필드 추가·필드 삭제·타입 변경(넓힘 포함)·필수→선택은 BREAKING이다.
- **검사 도구**: 세 단계로 검사한다.
  - `asyncapi validate`: 문법
  - `asyncapi diff`: 채널·토픽 수준 변경
  - 호환성 스크립트: 페이로드. `json-schema-diff`로 두 방향을 판정하고, 이 도구가 판정하지 않는 키워드(`enum`·`const`·`format`·`pattern` 등)가 바뀌면 실패시킨다
- **BREAKING 절차**: 기존 메시지를 고치지 않는다. V2 메시지를 같은 채널에 추가해 병행 발행하고, 컨슈머 전환 후 V1을 지운다.
- **Schema Registry를 두지 않는다**: 스키마의 원본은 AsyncAPI 문서 하나다. 런타임 강제는 생산자의 발행 전 검증(ajv)으로 대신한다.

## 결과

- 메시지 값이 도메인 데이터 그대로라 컨슈머·디버깅 도구가 봉투를 벗길 필요가 없고, 표준 헤더라 추적·라우팅 도구가 그대로 읽는다
- 호환성 판정이 별도 서비스 없이 CI에서 끝난다(메모리 예산, ADR 0014)
- 대가와 보완책
  - "필드 추가는 호환"이 아니라 "선택 필드 추가만 호환"이다. 필수 필드는 처음부터 넣거나 V2로 간다 → `architecture.md` 계약 규칙을 같은 기준으로 고친다
  - `json-schema-diff`(1.0.0)는 draft-07 기준이고 일부 키워드를 무시한다 → 무시하는 키워드의 변경은 실패시키고 수동 검토, 2019-09 이후 키워드는 쓰지 않는다
  - 컨슈머가 모르는 `ce_type`은 건너뛰고 커밋한다 → 새 이벤트를 받을 컨슈머를 생산자보다 먼저 배포한다
  - 런타임에 등록되지 않은 스키마를 막는 장치가 없다 → 발행 전 검증 + CI 검사 + 리뷰. 검증 위치(아웃박스 기록 시점)와 V1 제거 PR의 CI 예외 방법은 1단계에서 정한다
  - AsyncAPI CLI는 사용 통계를 기본으로 보낸다 → 로컬에서 끄고, CI(`CI=true`)에서는 보내지 않는다

## 검토한 대안

- **CloudEvents structured 모드 / 자체 봉투(값에 `{ meta, data }`)**: 메시지 하나로 완결되지만 컨슈머마다 봉투를 벗겨야 하고, 헤더 기반 도구가 메타데이터를 읽지 못한다
- **`asyncapi diff`만 사용**: 페이로드 변경(필드 삭제, 타입 변경)을 모두 `unclassified`로 두고 종료 코드 0으로 통과시켰다. 토픽 주소 변경만 breaking으로 잡았다
- **Confluent Schema Registry(8.4.0)**: 등록된 스키마 하나를 생산자·컨슈머 양쪽으로 써서, 컨슈머도 엄격하다고 가정한다. 닫힌 모델 FULL은 선택 필드 추가를 막아 필드 하나마다 V2가 필요하고, 닫힌 모델 BACKWARD는 타입 넓힘·필수→선택을 놓쳤다. 열린 모델은 선택 필드 추가를 일부러 막는다. 서비스 하나(JVM)가 더 필요하다

# ADR 0018: 웹 앱의 API 주소: 빌드에 박지 않고 실행 시점에 환경 변수로 주입한다

- 상태: ADR 0020으로 대체됨
- 날짜: 2026-10-30

## 맥락

ADR 0017에서 API 주소는 생성 클라이언트의 실행 시점 설정으로 정하기로 했고, queryKey에 `baseUrl`이 들어가므로 서버와 브라우저가 같은 값을 써야 한다. 어디서 그 값을 받을지는 첫 앱(스토어, shop-sim-web#14)으로 미뤘다.

- 배포는 CI가 이미지를 빌드하고 PC가 받아 staging·production을 별도 compose 프로젝트로 돌린다. 주소는 환경 변수로 받아 코드 변경 없이 바꾼다(ADR 0010, 0014).
- Next.js는 `NEXT_PUBLIC_*` 변수를 빌드할 때 브라우저 번들에 문자열로 넣는다. 그 밖의 변수는 서버에서만 읽힌다.
- App Router는 layout과 page를 병렬로 렌더링한다. layout에서 서버 쪽 설정을 하면 page가 먼저 API를 부를 수 있다.

## 결정

- **변수**: `API_BASE_URL` 하나. 서버와 브라우저가 같은 값을 쓴다.
- **서버**: `packages/api-client`가 모듈 로드 시 실행 환경의 `API_BASE_URL`을 읽는다.
- **브라우저**: 루트 layout이 요청 시점(`connection()`)에 같은 변수를 읽어 클라이언트 Provider에 넘기고, Provider가 첫 요청 전에 기본 클라이언트의 `baseUrl`을 맞춘다(`setBrowserBaseUrl`).
- **값이 없을 때**: 상대 경로로 조용히 요청하지 않고 페이지가 500으로 실패한다.
- **값의 출처**: 로컬은 web 레포 `mise.toml`(목 서버), 배포 환경은 compose가 넣는다.
- 셀러센터·어드민 SPA도 같은 원칙을 따른다(빌드에 박지 않는다). 전달 방식은 SPA 빌드 도구를 정할 때 정한다.

## 결과

- 이미지 하나를 환경 변수만 바꿔 staging·production에 쓴다. 주소를 바꿔도 다시 빌드하지 않는다(같은 빌드에 값만 바꿔 실행해 확인)
- 대가와 보완책
  - 루트 layout이 요청마다 렌더링되어 스토어의 모든 페이지가 동적이다. CDN의 HTML 캐시와 ISR을 쓸 수 없다. 지금 상품 화면은 요청 쿠키를 읽어 원래 동적이라 실제로 잃는 것은 홈과 404 정도다 → 공지·FAQ나 비로그인 상품 캐시처럼 정적 렌더링이 필요해지면 아래 대안 2·3을 다시 검토한다
  - 값이 RSC payload에 실려 HTML에 보인다 → 공개해도 되는 값만 이 방식으로 넘긴다
  - 서버도 브라우저와 같은 공개 주소(`api.<도메인>`)로 요청해 터널을 거쳐 돌아온다. 내부 주소를 쓰면 queryKey가 달라진다 → 서버 렌더링 지연이 문제가 되면 queryKey에서 `baseUrl`을 빼는 방법과 함께 다시 본다

## 검토한 대안

1. **빌드 시 인라인(`NEXT_PUBLIC_API_BASE_URL`)**: 코드가 가장 단순하고 정적 페이지가 남는다. 그러나 환경마다 이미지를 다시 빌드해야 하고, turbo는 `NEXT_*`를 태스크에 넘기면서도 캐시 해시에 넣지 않아 `build.env`에 적지 않으면 다른 환경의 값이 든 결과물을 캐시에서 복원한다
2. **브라우저가 자기 도메인에서 계산(`store.` → `api.`)**: 값을 넘길 필요가 없어 정적 페이지가 남는다. 그러나 서버 환경 변수와 도메인 규칙이 어긋나면 queryKey가 어긋나는데 그 결합이 코드에 숨고, 로컬(`localhost:3000` → `localhost:4010`)에는 규칙이 맞지 않는다
3. **Partial Prerendering**: 주소를 넘기는 부분만 동적으로 두고 나머지는 정적으로 남긴다. 지금 단계에서 도입하기에는 개념이 크다
4. **layout에서 서버 기본 클라이언트도 설정**: layout과 page가 병렬로 렌더링되어 page가 설정 전에 API를 부를 수 있다
5. **스토어를 거치는 같은 출처 경로(`/api`)**: 브라우저는 상대 경로, 서버는 절대 주소가 되어 `baseUrl`이 달라지고 queryKey가 어긋난다. API를 하위 도메인으로 공개한다는 결정(api 스펙 `servers`)과도 다르다

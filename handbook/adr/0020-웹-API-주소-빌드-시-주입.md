# ADR 0020: 웹 앱의 API 주소: 빌드 시 프레임워크 관례대로 주입한다

- 상태: 채택
- 날짜: 2026-10-30
- 대체: ADR 0018

## 맥락

ADR 0018은 이미지 하나를 환경 변수만 바꿔 쓰려고 API 주소를 실행 시점에 주입하기로 했다. 그러나 앱 종류마다 예외가 생겼다.

- 스토어(Next.js): 루트 layout을 요청 시점에 렌더링(`connection()`)해야 값을 읽을 수 있어 모든 페이지가 동적이 됐고, 서버와 브라우저에 값을 따로 전달하는 코드(`setBrowserBaseUrl`)가 필요했다.
- 셀러센터·어드민(SPA, ADR 0019): 정적 파일만 내려주므로 정적 파일 서버 단계에 설정을 내려주는 장치를 따로 만들어야 한다.

앱마다 다른 장치가 필요한 원칙은 보편적인 결정이 아니라고 판단했다. 두 프레임워크 모두 브라우저에 공개하는 값을 빌드할 때 번들에 넣는 관례가 있다.

## 결정

- **주입 시점**: 빌드할 때. 환경(staging·production)마다 이미지를 따로 빌드한다.
- **변수 이름**: 각 프레임워크 관례를 따른다. 스토어는 `NEXT_PUBLIC_API_BASE_URL`, SPA는 `VITE_API_BASE_URL`. 접두어가 "브라우저에 공개되는 값"임을 이름으로 드러낸다.
- **공용 코드**: `packages/api-client`가 두 이름을 모두 읽는다. 번들러가 자기 표현식(`process.env.NEXT_PUBLIC_*`, `import.meta.env.VITE_*`)만 치환하므로 공용 패키지가 번들러별 이름을 안다. 앱은 store(Next)와 셀러센터·어드민(Vite) 두 종류로 정해져 있어 이 결합을 받아들인다.
- **값이 없을 때**: 빌드를 실패시킨다.

## 결과

- 앱마다 별도 주입 장치가 없고, 서버와 브라우저가 같은 번들 값을 써서 queryKey의 `baseUrl`이 구조적으로 같다
- 스토어의 정적 페이지와 ISR을 다시 쓸 수 있다(0018의 대가가 사라진다)
- 대가와 보완책
  - 환경마다 이미지를 따로 빌드하고, 주소를 바꾸면 다시 빌드한다 → 배포 워크플로가 환경별로 빌드한다(infra 재사용 워크플로 항목)
  - turbo 캐시가 다른 환경의 값이 든 결과물을 복원할 수 있다(turbo는 `NEXT_*`를 태스크에 넘기면서 해시에 넣지 않는다) → 앱 `build` 태스크의 `env`에 변수를 적어 해시에 넣는다
  - 번들러가 늘면 api-client가 그 표현식을 더 읽어야 한다 → 새 번들러를 들일 때 이 ADR을 다시 본다
  - 이 방식으로 넣은 값은 누구나 번들에서 볼 수 있다 → 공개해도 되는 값만 넣고 비밀값은 서버 전용 변수로 둔다
  - 서버도 브라우저와 같은 공개 주소로 요청한다(queryKey 제약, 0018과 같음) → 서버 렌더링 지연이 문제가 되면 다시 본다

## 검토한 대안

- **실행 시점 주입(ADR 0018)**: 이미지 하나로 모든 환경을 쓴다. 그러나 위 맥락처럼 앱마다 예외 장치가 필요했다
- **이름 하나(`API_BASE_URL`)를 각 앱 설정이 치환**: Next는 `next.config`의 `env`, Vite는 `define`으로 같은 이름을 바꾸면 api-client가 번들러를 모른다. 그러나 접두어 없는 이름이 브라우저 번들에 들어가 공개 값임이 이름으로 드러나지 않고, 프레임워크 관례에서 벗어난다
- **앱이 시작할 때 값을 넘겨줌(`configureApiClient`)**: api-client가 환경 변수를 모른다. 그러나 Next 서버에서 모든 요청보다 먼저 호출되는 지점을 보장하기 어렵고, 빠뜨려도 조용히 넘어간다

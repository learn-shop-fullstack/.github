# ADR 0025: 배포 에이전트: infra 레포가 배포 상태를 소유하고 PC가 따라간다 (GitOps)

- 상태: 채택
- 날짜: 2026-10-31

## 맥락

배포는 pull 방식이고 에이전트 도구는 1단계에서 정하기로 했다(ADR 0014). 이미지는 `sha-<7자>` 태그로 GHCR에 올라가고 움직이는 태그가 없어, 에이전트가 무엇을 배포할지 알 방법을 함께 정해야 한다(ADR 0024).

- 운영은 PC 한 대의 compose 프로젝트 두 개(production, staging)다. 앱 이미지는 `*_IMAGE` 환경 변수로 받는다(shop-sim-infra#8)
- 사람이 손으로 배포하지 않고, PC에서 바꾼 운영 설정은 레포에 반영될 때까지 미완료다(infra 레포 규칙)
- 14단계는 Argo CD GitOps(앱 레포는 이미지 태그만 올리고 infra가 배포 상태를 소유)다
- 레지스트리를 감시해 컨테이너를 바꾸는 대표 도구 Watchtower는 2025-12에 아카이브됐다

## 결정

- **배포 상태**: 환경마다 배포할 이미지 태그를 infra 레포의 파일(`deploy/<환경>.env`, `API_IMAGE=…:sha-…` 형식)에 둔다. 이 파일과 compose 파일의 main이 그 환경의 원하는 상태다.
- **에이전트**: PC의 셸 스크립트를 launchd가 1분마다 실행한다. 운영 전용 infra 클론에서 main을 받아, 마지막으로 적용한 커밋과 다르면 환경마다 `docker compose pull`과 `up -d --wait`를 한다. 비밀값은 `~/.config/shop-sim/<환경>/`의 env 파일을 함께 넘긴다(ADR 0023). 적용 결과(커밋, 성공 여부)를 로그로 남긴다.
- **실패 처리**: 적용이 실패하면 자동으로 되돌리지 않는다. 다음 커밋까지 다시 시도하지 않고, 사람이 고치는 PR이나 되돌리는 PR을 낸다.
- **태그 갱신**: 앱 레포 CI가 이미지를 올린 뒤 infra에 staging 태그를 바꾸는 PR을 연다. 권한은 org GitHub App(infra 레포에 contents·pull requests 쓰기)으로 얻는다. 앱 레포에는 App ID(Variables)와 개인 키(Secrets)를 둔다. CI가 쓰는 첫 비밀값이다(ADR 0023의 범위).
- **승격**: production은 staging에서 확인한 같은 커밋 SHA의 태그로 바꾸는 별도 PR로 올린다. 웹 이미지는 두 환경 이미지를 같은 커밋에서 함께 빌드해 둔다(ADR 0020, 0024).
- **되돌리기**: 태그를 바꾼 PR을 revert한다. 에이전트가 이전 태그로 다시 맞춘다.

## 결과

- 어느 환경에 무엇이 배포됐는지와 그 이력이 infra 레포에 남고, 모든 배포가 PR 리뷰를 거친다
- compose 파일 변경도 같은 경로로 적용돼 PC에서 손으로 바꿀 일이 없다
- 14단계 Argo CD와 같은 모델이라 그대로 옮길 수 있다
- 대가와 보완책
  - infra main이 곧 운영이다. 머지하면 1분 안에 적용된다 → main 보호(PR 필수)를 유지하고, 운영 영향이 있는 PR은 리뷰 가이드에 되돌리는 방법과 다운타임을 적는다(infra 레포 규칙)
  - 앱 머지 한 번에 infra PR이 하나 더 생긴다 → 태그만 바꾸는 PR이라 리뷰는 짧다. 부담이 커지면 staging 자동 머지를 검토한다
  - App 개인 키가 새 비밀값이다. 유출되면 infra 레포에 쓸 수 있다 → App 설치를 infra 레포 하나와 필요한 권한으로 좁히고, 키는 api·web의 Secrets와 비밀번호 관리자에만 둔다. main 보호 때문에 키만으로는 머지할 수 없다
  - 1분 주기라 즉시 배포되지 않고, PC가 잠들면 멈춘다 → 학습 목적에는 충분하다. 상시 가동은 ADR 0014의 보완책을 따른다
  - 적용 실패를 사람이 알아채야 한다 → 처음에는 로그를 보고, 알림은 관측성 단계에서 붙인다
  - DB 마이그레이션 순서는 이 결정이 다루지 않는다 → api 첫 배포에서 정한다

## 검토한 대안

- **Watchtower류(레지스트리 감시)**: 설정이 거의 없다. 그러나 움직이는 태그가 필요하고(ADR 0024와 충돌) 배포 이력이 레포에 남지 않으며, 대표 도구가 아카이브됐다
- **사람이 infra 태그 PR을 낸다**: 새 비밀값이 없다. 그러나 앱 머지마다 같은 수작업이 반복된다
- **staging은 에이전트가 GHCR의 최신 태그를 따라간다**: PR이 줄어든다. 그러나 staging 상태가 레포에 남지 않아 GitOps에서 벗어난다
- **앱 CI 토큰으로 fine-grained PAT**: App보다 만들기 쉽다. 그러나 개인 계정에 묶이고 만료마다 갈아야 한다. App은 실행마다 짧은 토큰을 발급한다
- **Komodo·Portainer 같은 배포 관리 도구**: 화면과 기능이 많다. 그러나 상주 서비스가 메모리 예산을 쓰고, 상태가 도구 안에 있어 레포가 원본이 아니게 된다
- **지금 k3s + Argo CD**: 최종 형태다. 그러나 14단계 학습 범위이고 1단계 compose 구성 위에 클러스터를 얹는 비용이 크다

# 작업 방식 (Working Agreement)

> 원본은 `.github/handbook/working-agreement.md`. 모든 레포의 CLAUDE.md가 이 파일을 불러온다.
> 이 프로젝트는 **회사에서 일한다고 가정**하고 진행한다. 개인 프로젝트라도 실제 회사의 작업 절차를 그대로 따른다.

## 1. Claude와의 협업: 아주 작게 짜고, 세밀하게 리뷰한다

아직 모르는 영역이 많아서, 직접 짜기보다 **작은 단위의 코드를 꼼꼼히 리뷰하면서 배우는** 방식으로 진행한다.

### 작업 단위
- 한 단계에 **개념 하나**만 다룬다. (예: "Postgres 연결 설정", "상품 단건 조회 쿼리", "재고 차감 트랜잭션", "AG Grid 서버 데이터소스")
- 변경량은 대략 **diff 50줄 이내, 파일 1~3개**. 넘어가면 더 쪼갠다.
- 설정·보일러플레이트·인프라도 예외 없이 같은 방식으로 나눈다. 한꺼번에 생성하지 않는다.

### 각 단계의 진행 순서
1. **착수 전 설명**: 이번 단계에서 무엇을 왜 하는지 2~3문장. 처음 나오는 개념은 짧게 설명하고, 대안이 있으면 왜 이걸 골랐는지 한 줄.
2. **코드 작성**
3. **리뷰 가이드**
   - 꼭 봐야 할 줄과 그 이유
   - 이 코드가 깨지는 경우(엣지 케이스, 실패 시나리오, 동시성)
   - 계약(스펙·이벤트)을 건드렸다면 소비자에게 미치는 영향
   - 내가 이해했는지 확인할 질문 1~2개
4. **확인 방법**: 실행·테스트 명령과 기대 결과
5. **내가 승인하기 전에는 다음 단계로 넘어가지 않는다.** 질문이나 수정 요청은 그 단계 안에서 해결한다.
- 승인된 단계마다 커밋한다.
- 이해 확인 질문에서 막히면, 그 부분은 내가 직접 다시 짜보겠다고 요청할 수 있다.

### 설명 원칙
- 백엔드·인프라 관용구(트랜잭션 경계, 커넥션 풀, 인덱스, 락, 리버스 프록시, 컨테이너 네트워크 등)가 처음 나올 때는 개념을 짚어준다.
- 마법처럼 보이는 코드를 그냥 두지 않는다. 데코레이터, DI, ORM, 미들웨어, 라이브러리 내부 동작(AG Grid 행 모델, ProseMirror 트랜잭션, Next.js 렌더링 경계)을 처음 쓸 때 설명한다.
- 라이브러리 API는 추측하지 말고 공식 문서 기준으로 작성하고, 버전에 따라 다른 부분은 명시한다.
- 새 기술을 도입할 때는 왜 필요한지와 대안을 짧게 설명한 뒤 진행한다. 큰 결정은 ADR로 남긴다.

## 2. 회사식 작업 절차

### 이슈
- 모든 작업은 GitHub Issue에서 시작한다. `ROADMAP.md` 항목을 착수할 때 이슈로 옮기고, 이슈 번호를 로드맵 항목 끝에 적는다.
- 이슈 템플릿: 배경 / 할 일 / 완료 조건 / 영향 범위(어느 레포, 어느 계약).
- 여러 레포에 걸친 작업은 상위 이슈 하나 + 레포별 하위 이슈로 나눈다.
- 라벨: 모든 이슈에 `type:*`, `stage:*`, 영향받는 레포의 `repo:*`를 붙인다. 레포 안의 이슈는 그 레포 하나, 상위 이슈는 영향받는 레포 전부.
- 진행 상황은 GitHub Projects 보드(Backlog → Ready → In Progress → In Review → Done)로 관리한다.
- Ready 기준: 템플릿 칸(특히 완료 조건)이 채워져 있고, 선행 작업이 끝났고, 작업 단위로 쪼갤 수 있을 만큼 범위가 분명하다. 곧 할 일이라도 이 기준을 못 채우면 Backlog.
- POC·조사 이슈의 완료 조건은 "성공"이 아니라 "결론이 났다"로 쓴다. POC 코드는 `poc/<주제>` 브랜치에 두고 main에 머지하지 않는다.

### 브랜치와 커밋
- 트렁크 기반: `main`은 항상 배포 가능한 상태. 작업 브랜치는 짧게 유지한다.
- 브랜치 이름: `<유형>/<이슈번호>-<짧은-설명>` (예: `feat/12-product-detail-api`)
- 커밋 메시지: Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`, `ci:`). 본문에 이유를 적고, 끝에 이슈 번호.

### PR
- `main` 직접 푸시 금지. 모든 변경은 PR로, CI 통과가 필수다.
- PR 템플릿(배경, 변경 내용, 테스트 방법, 영향 범위, 리뷰 포인트)을 채운다.
- PR 하나는 이슈 하나. 리뷰 가능한 크기를 넘으면 쪼갠다.
- 머지는 squash merge.

### 계약 변경
- HTTP·이벤트 계약 변경은 스펙 PR이 먼저다 (`architecture.md` "계약").
- 하위 호환을 깨는 변경은 PR 제목에 `BREAKING`을 붙이고, 소비 레포에 후속 이슈를 만든다.

### 결정 기록 (ADR)
- 기술 선택, 구조 변경, 되돌리기 어려운 결정은 `handbook/adr/`에 ADR로 남긴다.
- 결정을 바꿀 때는 기존 ADR을 수정하지 않고, 새 ADR을 쓰고 기존 것을 "대체됨"으로 표시한다.

### 환경과 배포
- 환경: local(각자 PC) / staging / production.
- 배포는 CI가 한다. 사람이 VM에 들어가 손으로 배포하지 않는다.
- 비밀값은 레포에 커밋하지 않는다. 레포에는 `.env.example`만 둔다.

### 릴리스
- 스펙 패키지와 앱은 semver 태그로 릴리스하고, 릴리스 노트를 남긴다.

### 운영
- 장애가 나면(시뮬레이터로 일부러 일으킨 것 포함) 런북대로 대응하고, 포스트모템을 남긴다: 무슨 일이 있었나 / 영향 / 원인 / 탐지와 대응 / 재발 방지.
